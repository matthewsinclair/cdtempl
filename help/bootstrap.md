# cdsync bootstrap

Hand the design system to a Claude Design project.

```
cdsync bootstrap [--delta] [--stdout] [--target PATH]
```

Writes `BOOTSTRAP-CD.md` into the target: the document a Claude Design project
reads to take on the design system held there.

## One generator, and the tree decides what comes out

Run it over an **empty** target and it emits what a **cold** Claude Design
project needs to build a design system from nothing. Run it over a **populated**
target and it emits everything a fresh project needs to **resume** from where the
last one stopped -- an inventory of what exists, the numbering high-water marks,
and any addenda waiting to be absorbed.

Same command, same document, content following the tree's state. Cold or warm is
**measured, never declared**: there is no `--cold` flag, because a flag would let
you assert a state the tree contradicts, and a "resume" over an empty tree tells
Claude Design not to build the thing that is not there.

## Why it exists, which is not the obvious reason

**Bootstrap is an invariant before it is a workflow.**

`design/system/` is the single source of truth for a project's design system, and
Claude Design is a clamp-on tool used to work on it. That claim is only worth
something if it can be tested, and this is the test: **if a cold Claude Design
project can be reconstructed from the tree alone, nothing important is hiding in
a chat log.**

The normal working relationship stays a long-running Claude Design project synced
each round. This is the guarantee underneath it, not the routine.

Which is why it is **regenerated by every `install` and `import`** rather than by
a command someone remembers to run. Its use is rare; its currency has to be
continuous, because an unexercised guarantee is a claim. Exercise it occasionally
against a real project, or the first time it is needed will be the first time it
is tried.

## The inventory lists everything, and that is load-bearing

The document tells Claude Design to export every path it names, so a path it
fails to name is a path the next export omits and the install then removes.

So the listing rule is inverted: **every top-level entry appears unless another
section of the same document already accounts for it.** The exceptions are
`addenda/` (its own section, and it must never come back), `_inbox/` (named in
the contract block as none of Claude Design's business), `index.md` (its own
present-or-absent line), this document itself, and `assets/` — but only when the
asset table above it actually listed something.

That last condition is the one that bit. The asset table walks
`assets/<slug>/` **subdirectories**, and three of the four real projects keep
flat files in `assets/` instead. The table printed nothing, the listing skipped
the directory assuming the table had it, and seven tracked files — a logo and an
app icon among them — appeared nowhere in a document that says "export every
path listed here".

Counts are of the deliverable rather than the disk: `.DS_Store` is excluded, so
the number is one Claude Design can reconcile against.

## It is protected from the drop

`BOOTSTRAP-CD.md` is declared in `CDSYNC_DROP_PROTECTED_PATHS` alongside
`addenda/` and `cdsync.json`. It is Cdsync's output living inside a tree Claude
Design replaces wholesale, so without that declaration an export would silently
eat it.

The three are protected for different reasons: `addenda/` is written by the
project *about* a drop and flows **back**; `BOOTSTRAP-CD.md` is written by
Cdsync *for* Claude Design and flows **out**; `cdsync.json` is the venture's
own facts and order, living at the tree root, and flows **nowhere** -- a drop
may not deliver one either.

## `--delta`

```
cdsync bootstrap --delta
```

Writes `RETURN-DELTA.md`: what changed on the repository side since the last
export, for a project that **already holds** the design system. The addenda and
the numbering, without the whole adoption document.

The inbound leg was always tooled -- archive into `_inbox/`, Cdsync unpacks it.
This is the outbound leg. Canon says an addendum flows back to Claude Design and
retires when a drop absorbs it; it said *that* it flows back and never *how*, and
before this the answer was a human carrying notes in `~/Downloads`.

## Options

| Option | Effect |
|---|---|
| `--delta` | Emit the since-your-last-export document instead of the adoption one |
| `--stdout` | Print it and write nothing |
| `--target PATH` | Override the target for this invocation |

## What it tells Claude Design

Beyond the inventory and the numbering, three rules the programme has paid for:

- **Export the whole tree, always.** Not a delta, not the changed parts. The
  receiving side replaces what it has, so a partial export reads as a deletion of
  everything left out.
- **Corrections land at source.** A fix that lives only in a delivery note is
  reverted by the next export.
- **Never allocate an identifier blind.** The high-water marks are in the
  document. If they are not, ask rather than assume -- a collision here cost a
  full export cycle on both sides.
