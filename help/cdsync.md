# cdsync

Bootstrap a venture with Claude Code and Claude Design.

Cdsync regularises the Claude Design process for a set of problems that recur across
ventures. The goal is **regular and predictable** first, **automated** second — the
first matters considerably more. If the whole process were run by hand and never
scripted, the regularity would still be most of the value.

## The loop

1. `cdsync new <name>` scaffolds a venture locally.
2. `cdsync bootstrap` writes `BOOTSTRAP-CD.md` into the target — the document a Claude
   Design project reads to take the design system on.
3. `cdsync brief` assembles a complete brief from the spec library and the venture's
   own facts.
4. Claude Design works to that brief and exports a zip.
5. **`cdsync install <zip>` for an as-is export, `cdsync import <zip>` for a converted
   drop.** See below — they are not variants of each other.
6. `cdsync check` holds the drop against its own specifications.
7. `cdsync site` stands the content up somewhere you can look at it.
8. The venture project takes what it needs out of the target, deliberately and by
   hand.

Iterations repeat 3–7. Nothing downstream moves until someone decides it should.

## `install` or `import` — the one choice that can destroy work

They take different artefacts and have opposite semantics, and picking the wrong one is
the most destructive mistake available in this tool.

| | `import` | `install` |
|---|---|---|
| Takes | A **converted** drop — a subset, the five owned paths | An **as-is** export — the whole tree |
| Does | Merges. What is in the target and absent from the drop **survives** | Replaces. What is in the target and absent from the drop is **removed** |
| Wrong tool | Delivers a tenth of the drop and reports the rest as `ignore` | Deletes the venture set, the microsite, the prototypes |

**An as-is export is the whole tree, so it is installed. A converted drop is a subset of
it, so it is imported.** Being Cdsync-shaped is not the discriminator; being a *subset* is.

**Hand-unzipping a drop is never correct.** `install` refuses over uncommitted or
untracked content under the target, because git being able to give the tree back is what
makes a replace safe — there is no backup directory, on purpose.

**Every lane between here and Claude Design passes through a human.** There is no
automated path in either direction: the brief goes across as an upload or a paste,
and the drop comes back as a downloaded zip.

## The target

`$CDSYNC_TARGET` defaults to `design/` and may point anywhere. What is standardised
is the structure underneath it, never the location:

```
$CDSYNC_TARGET/
  RETURN.md              this drop's narrative -- mandatory
  brief.md               the order this drop answers
  index.md               manifest: every asset, its status, its spec version
  kit/                   the neutral kit every artefact imports
  assets/<slug>/         flat, one directory per asset
  notes/                 durable thinking that is not an asset
  site/                  generated by `cdsync site`
  BOOTSTRAP-CD.md        generated by `cdsync bootstrap` -- protected, no install writes it
  addenda/               repo-authored corrections -- protected, no install writes it
  _inbox/                delivery archives; ephemeral transport, git-ignored
```

`assets/`, `kit/`, `notes/`, `index.md` and `RETURN.md` are the five paths Claude Design
owns. `addenda/` and `BOOTSTRAP-CD.md` are repo-authored and **no install path may
overwrite either**; a name declared both owned and protected makes the contract
unsatisfiable, and both install paths refuse rather than pick a winner.

Resolution order: `--target`, then `$CDSYNC_TARGET`, then `cdsync.json`, then
`design/`.

A target outside the repository does not version with the project. That is correct
for a shared or confidential drop and wrong by accident, so every command that
resolves one says which it got.

`assets/` is flat deliberately. Grouping is an order in disguise, and eight asset
types are genuinely both design and venture, so any grouping forces a lie about
them. The grouping lives in `index.md` as data instead.

## Cdsync never writes into the application

The target is the **as-designed** record. The application is the **as-built**.

`import` writes only `assets/`, `kit/`, `notes/`, `index.md` and `RETURN.md` inside
the target, and touches nothing else anywhere. That is what stops a later drop
clobbering work built on an earlier one, and what lets you hold intent against
implementation and see where they diverged.

It also means a venture can keep its own files in the target, and `cdsync site` can
generate into it, without a drop eating either.

**`install` is wider by design and still stops at the same boundary.** It replaces the
whole target, because an as-is export *is* the whole target — but the target is still the
entire output boundary. Nothing outside `$CDSYNC_TARGET` is written by any command.

## Commands

| Command | What it does | What it knows |
|---|---|---|
| `cdsync new <name>` | Scaffold a venture | **All** application knowledge lives here |
| `cdsync init` | Start a design system in a repository that already exists | Only the target |
| `cdsync bootstrap` | Write `BOOTSTRAP-CD.md` into the target | The target's own state |
| `cdsync brief` | Assemble the brief | The spec library |
| `cdsync install <zip>` | **Replace** the target with an as-is export | Only the target |
| `cdsync import <zip>` | **Merge** a converted drop into the target | Only the target |
| `cdsync check` | Hold a drop against its specs | The spec library and the target |
| `cdsync site` | Stand up the microsite | Only the target |
| `cdsync release` | Read the version, move it, cut a release | `VERSION` and git |
| `cdsync doctor` | Diagnostics | — |

`brief`, `install`, `import`, `check` and `site` know nothing about Phoenix, Ash or
Laksa. That confinement is what keeps both install paths dumb, which is what keeps them
safe.

`bootstrap` is a generator with one output and two shapes: run over an empty target it
describes what to build, run over a populated one it describes how to resume. **Cold or
warm is measured, never declared** — there is no `--cold` flag, because a flag would let
you assert a state the tree contradicts.

## The spec library

`specs/` holds the definition of done for each asset, plus the taxonomy of fifty-two
types and the seven bundles. `brief` assembles from it; `check` compares a drop against
it.

A drop carries a stamped copy of each spec it delivers. The library here is the
source of truth, and the version difference between the two is what makes staleness
detectable.

Run `cdsync doctor` to see the library's version and how much of the taxonomy is
specified.
