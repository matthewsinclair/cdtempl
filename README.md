# Cdsync

Manage a project's design system in and out of Claude Design.

Cdsync is a shell CLI. It does not design anything. It creates the tree a design system lives in, generates the documents Claude Design reads, unpacks what Claude Design sends back, and holds the result against its own specifications. The design is Claude Design's job; the custody of it is Cdsync's.

```
cdsync init --target <repo>/design/system      # start a design system
cdsync bootstrap --target <repo>/design/system # write the document CD reads
# ... Claude Design runs a round and exports an archive ...
cdsync install <archive> --target <repo>/design/system
cdsync check --target <repo>/design/system
```

## The one thing to understand first

**`design/system/` is the single source of truth for a project's design system, and Claude Design is a clamp-on tool used to work on it.**

That inverts how this normally goes, and it is deliberate. While the authoritative copy lived inside a Claude Design project, the truth sat somewhere that could not be diffed, reviewed or reverted. Corrections had to be carried into a chat by hand and hoped for. A delivery could be *ahead* of its repository as easily as behind it. Identifiers were allocated blind and a collision cost a full export cycle on both sides.

With the tree authoritative: a correction is a commit, the high-water marks are in the material, and truth has one direction with a rest point where the repository always wins.

Four consequences that decide almost every question you will have:

- **The tree is specification, not running code.** Requirements and information. **Nothing in the application reads from it at runtime** -- if an import path, a build step or a stylesheet ever reaches into it, that is a defect in the project. A reference the runtime depends on has stopped being a reference.
- **It is tracked in full**, so the specification can be diffed against the implementation at the revision the code was at. One exclusion: `system/_inbox/`, the drop-off point for delivery archives, which are ephemeral transport.
- **It is never hand-edited.** It changes through a round with Claude Design, mediated by Cdsync. The single sanctioned exception is `addenda/`.
- **It is an end-state view.** The project will not arrive there in one jump, so **a gap between the tree and the application is expected and is never a defect**. Anything comparing the two reports distance from the end state, which is information.

The full statement of this is `intent/docs/design-system-lifecycle.md`, and it is canon: if anything else in this repository disagrees with it, the other thing is a defect.

## The loop

1. **`cdsync init`** (or `cdsync new`) creates the tree.
2. **`cdsync bootstrap`** writes `BOOTSTRAP-CD.md` into it -- the self-contained document a Claude Design project reads to take the design system on.
3. **Claude Design runs a round** and exports what it holds as an archive.
4. The archive lands in `_inbox/`, and **`cdsync install`** unpacks it into the tree.
5. **`cdsync check`** holds the result against its specifications. **Gaps are recorded in `addenda/`, never repaired in place.**
6. **`cdsync brief`** assembles the next round's order, and it starts again.

`bootstrap` is regenerated by every `install` and `import` rather than by a command someone remembers to run. Its use is rare; its currency has to be continuous, because **an unexercised guarantee is a claim** -- and this one is the test of the whole arrangement. If a cold Claude Design project can be reconstructed from the tree alone, nothing important is hiding in a chat log.

## Getting started

### Requirements

`bash`, plus three things `cdsync doctor` gates on:

| Dependency | For |
| ---------- | --- |
| `jq`       | reading `cdsync.json` and `kit/tokens.json` |
| `unzip`    | unpacking a Claude Design drop |
| `python3`  | serving the microsite |

Run `cdsync doctor` first. It reads and reports; it writes nothing, anywhere.

### The common case: a project that already exists

Two commands. Everything else is Claude Design's turn.

```
cdsync init      --target /path/to/repo/design/system
# fill in design/system/cdsync.json -- especially fixed, open and order
cdsync bootstrap --target /path/to/repo/design/system
```

Then commit the tree in that project's own repository and hand `BOOTSTRAP-CD.md` to a Claude Design project.

`init` also writes a `.gitignore` in the target's **parent**, holding one anchored rule: `/system/_inbox/`. It lives outside the target because `install` replaces the target wholesale, so a guard inside it would not survive the first delivery it exists to protect against. It never truncates an existing `.gitignore` -- it appends, and only when the rule is absent.

**Nothing else of Cdsync's belongs in that project.** No outbox, no handover scaffolding, no agent contract. The one exception is `cdsync.json`, the venture's own facts and order: it lives at the design tree root -- one home for `new` ventures and `init` projects alike -- which is what makes `brief` runnable for a project Cdsync does not own. No install path may overwrite it, and a drop may not deliver one.

### A brand-new venture

```
cdsync new acme
```

Creates `./acme/` as **its own git repository**, with the venture's facts in `design/cdsync.json` at the tree root, an agent contract in `AGENTS.md` and `CLAUDE.md`, and the target skeleton under `design/`. Its `.gitignore` covers the generated `design/site/` and, like `init`, the target's `_inbox/`. Fill in `design/cdsync.json` -- especially `fixed`, `open` and `order` -- then `cdsync brief`.

### `init` or `new`, and why it is not a flag

They are not variants of each other. The question is **what the new thing is**.

| The new thing | Command | You get |
| ------------- | ------- | ------- |
| A **venture** | `cdsync new <name>` | Its own repository, the agent contract, the skeleton, `cdsync.json` at the tree root |
| A **design system**, in a project that already exists | `cdsync init` | The skeleton and the `cdsync.json` stub, in the repository you are already in |

Running `new` against an existing project would `git init` a second repository nested inside the first and write three files the canon forbids there.

## The commands

Nine, one job each. `cdsync help <command>` for any of them.

| Command | What it does | What it knows |
| ------- | ------------ | ------------- |
| `cdsync new <name>` | Scaffold a venture | **All** application knowledge lives here |
| `cdsync init` | Start a design system in an existing repository | Only the target |
| `cdsync bootstrap` | Write `BOOTSTRAP-CD.md` into the target | The target's own state |
| `cdsync brief` | Assemble the round's order for Claude Design | The spec library |
| `cdsync install <zip>` | **Replace** the target with an as-is export | Only the target |
| `cdsync import <zip>` | **Merge** a converted drop into the target | Only the target |
| `cdsync check` | Hold a drop against its specifications | The spec library and the target |
| `cdsync site` | Stand up the microsite over the target | Only the target |
| `cdsync doctor` | Diagnostics | -- |

Every command except `doctor` takes `--target PATH`. The target defaults to `design/` and may be pointed anywhere; **what is standardised is the structure underneath it, never the location.**

## Two install paths, and choosing wrong is the most destructive thing here

| The artefact | Command | What it does |
| ------------ | ------- | ------------ |
| An **as-is export** -- the whole tree | `cdsync install` | **Replaces.** What the drop does not carry is removed, and every removal is printed |
| A **converted drop** -- a subset, the five owned paths | `cdsync import` | **Merges.** What the drop does not carry survives |

An as-is export *is* the whole tree, so it is installed. A converted drop is a *subset* of it, so it is imported. Reach for the wrong one and either the venture set, the microsite and the prototypes are deleted, or nine-tenths of the drop is reported as `ignore` and dropped on the floor.

**Hand-unzipping a drop is never correct.** `install` refuses over a target holding uncommitted or untracked content, because the tree being tracked in full is what makes a replace reversible: git holds every prior state, so the tool's job is to prove that copy is complete rather than to make another one. There is **no backup directory**, by design. `addenda/` and anything gitignored survive regardless.

Use `--dry-run` when unsure. **The top-level plan is not the removal audit** -- it lists top-level paths only, so a file deleted *inside* a replaced directory never appears in it. `git status` after the install is where the removals actually are.

## What the tree looks like

```
design/system/
  BOOTSTRAP-CD.md   what a Claude Design project reads to take this on
  RETURN.md         this round's narrative -- what was done, what could not be
  brief.md          the order this round answers, if there was one
  index.md          manifest: every asset, its status, its spec version
  kit/              the neutral kit every artefact imports
  assets/<slug>/    flat, one directory per asset, each with a spec.md
  notes/            durable thinking that is not an asset
  addenda/          REPO-AUTHORED. Protected. No install path overwrites it
  _inbox/           delivery archives. Ephemeral transport, gitignored
```

`import` writes exactly five of these: `assets/`, `kit/`, `notes/`, `index.md`, `RETURN.md`. **Cdsync never writes into the application** -- the whole output boundary is the target.

## The spec library

`specs/` holds **27 specifications against a 52-slug taxonomy, plus 7 bundles**. A specification says what an asset is and what *finished* means for it. A drop carries a stamped copy of each spec it delivers; the library holds the original those copies are stamped from, and the version difference between the two is what makes staleness detectable.

A slug can be legitimately named as a dependency long before it is specified, and 25 of the 52 are in that state. `cdsync check` reports an unwritten dependency as advisory, which is right -- it resolves when the spec is written.

### The two version numbers

**`spec_version` is the library's stamp, not a per-drop counter.** It records which version of the library specification an asset was built from, copied unchanged. Claude Design does not increment it, and a new draft of the same asset against the same specification carries the same number as the last one. **An asset ordered ahead of the library stamps the literal `unassigned`** -- there is no number to copy, and a self-chosen one is the counter this rule exists to stop; when the library gains the entry, `check` asks for a rebuild against it.

That is the whole point: the comparison is what makes it useful. **A number each side increments on its own schedule cannot measure a distance**, because it never disagrees for a reason. An asset's own progress is `status` and `coverage`.

`kit_version` works the same way, against the kit.

**Where the library has no entry for an asset, the correct answer is no number at all** -- leave the field out rather than invent one. That is the commoner case, not the edge.

## `cdsync check`: six rules

Two block, four advise. Exits non-zero if a blocking rule fails.

| # | Rule | Severity |
| - | ---- | -------- |
| 1 | `status: complete` alongside non-zero blanks is a contradiction | **blocking** |
| 2 | A drop's stamped `spec_version` against the library, to detect staleness | advisory |
| 3 | Illustrative numbers must be visibly marked in the artefact | advisory |
| 4 | Every colour literal must appear in `kit/tokens.json` | **blocking** |
| 5 | `status: partial` requires `coverage`; `complete` requires it to be total | advisory |
| 6 | `classification` is declared, is a known value, and is not conflated with `audience` | advisory |

The split is deliberate. Rule 4 is the leak guard that makes neutrality a property of the repository rather than of whoever last touched a file; rule 1 is a drop lying about its own state. The rest report distance, and **distance from an end state is information, not failure.**

**A check that cannot see something does not pass it.** `check` refuses a target holding no slug directories rather than reporting clean, because zero checked is a failure and not a clean bill of health.

## Concepts you will meet

**`status` and `coverage`.** `spec-only`, `draft`, `partial`, `complete`. An asset whose parts share one definition of done takes `partial` plus `coverage` rather than splitting into several assets -- its parts are one specification applied N times, not N specifications. Coverage may be a fraction where one is computable, or prose where it is not.

**`classification`.** `public`, `internal`, `confidential`. An axis of its own, not a flavour of `audience`. It governs **where material may be shown, never whether it is committed** -- everything is tracked regardless. It is not a delivery filter and must not be used as one. Declaring it also means taking the value back *out* of `audience`, which answers who a thing is *for*. `public` is the exception, being a real answer to both questions.

**`blanks`.** Computed by the tool, never hand-maintained.

**`addenda/`.** Repo-authored material *about* the design, written where the design has a gap, in the drop's own voice. It flows **back** to Claude Design and retires when a later drop absorbs it -- **verified by reading it, never by a receipt**. No install path overwrites it. It is not a place to design things.

**Cdsync never repairs a drop.** When a check finds a problem there are two honest outcomes and repair-in-place is not one: record the gap in `addenda/`, or refuse and send it back to be fixed at source. If Cdsync edits drop content, a re-export diff stops meaning *the design changed*.

## Things that will bite you

- **An empty result is not evidence until the probe is proven able to hit.** A uniform zero is a broken probe until shown otherwise -- real data is lumpy.
- **A check that cannot see a thing must not return a verdict about it.** The dangerous direction is always the one that reports absence.
- **`BOOTSTRAP-CD.md` regenerates on sync and on nothing else.** A repo-side edit has nothing to hang it on, so regenerate by hand after touching `addenda/` -- or after changing the generator, which stales every project's copy at once with no local symptom.
- **A generated document is not a report. It is an instruction the other side obeys.** A path it omits is a path the next export omits. Read every generated document against the tree before it is sent.
- **Two descriptions of one thing will disagree, and the terse one tends to survive.** Structural tests guard the ones that have already drifted.
- **A measurement taken on one project, written down without its scope, reads later as a verdict on all of them.** Write the scope into the sentence.

## Development

```
bats test/cdsync.bats          # the suite
bin/devbin test all            # the suite as a sealed gate: tmp/test/LATEST_SHELL.errors is empty only after a completed green run
shellcheck bin/cdsync lib/*.sh .claude/scripts/*.sh
cdsync doctor                  # installation, dependencies, spec library
```

The suite is the contract. Several tests are structural rather than behavioural -- every command the dispatcher accepts must have a help file and a row in the front page's command table, every flag a command implements must be documented in its help file, and the documented rule count must match the implemented one. Each exists because that exact drift happened.

**Mutation-test a new assertion in both directions before trusting it**: break the code, watch it go red, restore it. In this project, tests have been wrong rather than the code more often than the reverse.

Layout: `bin/cdsync` is the dispatcher, `bin/devbin` is the development launcher and not part of a release, `lib/*.sh` is one module per job, `specs/` is the library, `help/` is one page per command, `templates/` is what `new` scaffolds from. `intent/llm/MODULES.md` is the registry of which module owns what -- check it before creating a new one.
